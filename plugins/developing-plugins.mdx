## Overview

This guide walks you through building a plugin that extends roadbeat Studio. Plugins are self-contained NestJS modules that integrate with CE through well-defined extension points.

<Callout kind="info">
  Plugins import **only** from `@roadbeat/plugin-sdk` — never from CE source code directly. This ensures clean separation and forward compatibility.
</Callout>

## Getting Started

<Steps>
  <Step title="Create the plugin project">
    ```bash
    mkdir my-plugin && cd my-plugin
    npm init -y
    npm install @roadbeat/plugin-sdk
    npm install @nestjs/common @nestjs/core rxjs
    npm install -D typescript @types/node
    ```
  </Step>

  <Step title="Create the manifest">
    Create `manifest.json` in the plugin root:

    ```json
    {
      "id": "my-plugin",
      "name": "My Plugin",
      "version": "1.0.0",
      "requires": ">=0.1.0",
      "entry": "dist/index.js"
    }
    ```
  </Step>

  <Step title="Implement the plugin interface">
    Create `src/index.ts`:

    ```typescript
    import { RoadbeatPlugin } from '@roadbeat/plugin-sdk';
    import { MyPluginModule } from './my-plugin.module';

    class MyPlugin implements RoadbeatPlugin {
      readonly id = 'my-plugin';
      readonly name = 'My Plugin';
      readonly version = '1.0.0';
      readonly requires = '>=0.1.0';

      getModule() {
        return MyPluginModule;
      }
    }

    export default new MyPlugin();
    ```
  </Step>

  <Step title="Create the NestJS module">
    Create `src/my-plugin.module.ts`:

    ```typescript
    import { Module } from '@nestjs/common';
    import { MyPluginService } from './my-plugin.service';
    import { MyPluginController } from './my-plugin.controller';

    @Module({
      controllers: [MyPluginController],
      providers: [MyPluginService],
      exports: [MyPluginService],
    })
    export class MyPluginModule {}
    ```
  </Step>

  <Step title="Build and deploy">
    ```bash
    npx tsc
    cp -r dist/ manifest.json /path/to/studio/plugins/my-plugin/
    ```
  </Step>
</Steps>

<Callout kind="alert">
  Plugin backends are loaded **once, when the API starts**. After rebuilding a plugin, restart the API — the dev watcher (`nest start --watch`) only watches Studio's own sources, and touching a file is not enough. New SQL migrations are also applied on that restart.
</Callout>

## RoadbeatPlugin Interface

The `RoadbeatPlugin` interface is the contract between CE and plugins:

```typescript
interface RoadbeatPlugin {
  readonly id: string;
  readonly name: string;
  readonly version: string;
  readonly requires: string;

  getModule(): Type<any> | DynamicModule;

  // Optional
  getAdminRoutes?(): PluginAdminRoute[];
  getMenuItems?(): PluginMenuItem[];
  getEditorExtensions?(): PluginEditorExtension[];
  getDashboardWidgets?(): PluginDashboardWidget[];
  getEventHandlers?(): PluginEventHandler[];
  getPrismaSchemaPath?(): string;
  onPluginInit?(): Promise<void>;
  onPluginDestroy?(): Promise<void>;
}
```

| Method | Purpose |
|--------|---------|
| `getModule()` | NestJS module to register (controllers, services, providers) |
| `getAdminRoutes()` | Angular routes for admin UI pages |
| `getMenuItems()` | Sidebar navigation entries |
| `getEditorExtensions()` | Content editor sidebar panels or toolbar actions |
| `getDashboardWidgets()` | Dashboard widget components |
| `getEventHandlers()` | Event listener registrations |
| `getPrismaSchemaPath()` | Optional pointer to a schema file. The host's migration runner does not use it — it applies every `migrations/*.sql` file in the plugin directory (see [Database Extensions](#database-extensions)) |
| `onPluginInit()` | Called after module registration, before app starts |
| `onPluginDestroy()` | Called during graceful shutdown |

## Listening to Events

Use NestJS `@OnEvent()` decorators to listen to CE lifecycle events:

```typescript
import { Injectable } from '@nestjs/common';
import { OnEvent } from '@nestjs/event-emitter';
import { ContentEvents, ContentEventPayload } from '@roadbeat/plugin-sdk';

@Injectable()
export class MyService {
  @OnEvent(ContentEvents.AFTER_CREATE)
  async onContentCreated(payload: ContentEventPayload) {
    console.log(`Content created: ${payload.contentId}`);
  }

  @OnEvent(ContentEvents.AFTER_PUBLISH)
  async onContentPublished(payload: ContentEventPayload) {
    console.log(`Content published: ${payload.contentId}`);
  }
}
```

## Preventable Events

"Before" events extend `PreventableEvent`. Call `event.prevent()` to block the action:

```typescript
import { OnEvent } from '@nestjs/event-emitter';
import { ContentEvents, ContentBeforePublishEvent } from '@roadbeat/plugin-sdk';

@Injectable()
export class WorkflowGuard {
  @OnEvent(ContentEvents.BEFORE_PUBLISH)
  async checkApproval(event: ContentBeforePublishEvent) {
    const approved = await this.isApproved(event.contentId);
    if (!approved) {
      event.prevent('Content must be approved before publishing');
    }
  }
}
```

| Preventable Event | Can Modify Data |
|-------------------|-----------------|
| `ContentBeforeCreateEvent` | Yes (`event.data` is mutable) |
| `ContentBeforePublishEvent` | No |
| `ContentBeforeDeleteEvent` | No |
| `AssetBeforeDeleteEvent` | No |

## Feature Gating

Use `FeatureGateService` to check plugin and license status:

```typescript
import { FeatureGateService } from '@roadbeat/plugin-sdk';

@Injectable()
export class MyService {
  constructor(private featureGate: FeatureGateService) {}

  async doSomething() {
    if (this.featureGate.isPluginActive('pro-workflows')) {
      // Include workflow data
    }

    const maxUsers = this.featureGate.getLimit('max_users', 5);
  }
}
```

## Database Extensions

Plugins create their own database tables with plain SQL migration files in a `migrations/` folder next to the plugin's `manifest.json`:

```text
plugins/my-plugin/
├── manifest.json
├── dist/
└── migrations/
    ├── 001_create_tables.sql
    └── 002_add_status_column.sql
```

The Studio API applies them at startup, in file-name order, before your plugin module initializes, and records each file in the `plugin_migrations` table — see [Plugin database migrations](/plugins/overview#plugin-database-migrations). Write them so they can meet an existing schema:

- **Never edit an applied file.** A changed checksum is reported and the file is not re-run; add `003_…sql` instead.
- **Prefer idempotent DDL** (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`). The runner also treats "already exists" errors as "applied before" per statement, but other errors roll the whole file back and block your later files.
- **Cast bound values to the column type** in raw SQL (`$1::uuid`, `make_interval(days => $2::int)`) — PostgreSQL does not infer them reliably from a parameter.

<Callout kind="alert">
  All plugin tables **must** use a `pro_` prefix to avoid conflicts with CE tables (e.g., `pro_audit_logs`, `pro_workflow_states`).
</Callout>

## Validation and Errors

### DTO validation

Your DTOs are validated by the host's global `ValidationPipe`. Plugins live in their own workspace with their own `node_modules`, so the host resolves `class-transformer` and `class-validator` for code under `PLUGINS_DIR` to **its own copies** before any plugin entry is loaded. That keeps `@Type()` metadata and nested validation (`@ValidateNested()`) working for plugin DTOs — without it, arrays of nested objects arrived as arrays of empty arrays and nested validation silently did nothing.

```typescript
import { Type } from 'class-transformer';
import { IsArray, IsString, ValidateNested } from 'class-validator';

class StateDto {
  @IsString() id!: string;
  @IsString() name!: string;
}

export class SaveWorkflowDto {
  @IsArray()
  @ValidateNested({ each: true })
  @Type(() => StateDto)
  states!: StateDto[];
}
```

### Throwing errors

Throw Nest's HTTP exceptions with a **stable error code**, an English message and — when the message contains values — `params`:

```typescript
import { NotFoundException } from '@nestjs/common';

throw new NotFoundException({
  code: 'MY_PLUGIN_ITEM_NOT_FOUND',
  message: `Item ${id} not found`,
  params: { id },
});
```

- The host's exception filter passes `code`, `message` and `params` through unchanged, so clients — including the Studio UI — translate by `code` and fall back to `message`. See [Error Codes](/api-reference/error-codes).
- Your exceptions keep their status. They are built against the plugin's own `@nestjs/common`, so they are not `instanceof` the host's `HttpException`; the filter recognizes them by shape (`getStatus()` / `getResponse()`).
- Do not `throw new Error(...)` for client errors — it becomes a `500 INTERNAL_ERROR`. Map upstream failures (for example an external provider answering with an HTTP error) to a coded `502` instead.

### Translating error texts in your UI

Add one `errors.codes.<CODE>` entry per code to your plugin's UI catalogs (all 24 languages), using the same `{{param}}` placeholders as `params`. The admin UI's error helper resolves the translated text, falls back to the API's `message`, and finally to a generic text.

## Admin UI Extensions

Plugin frontends are built as **Angular web components** using `@angular/elements`:

### Naming Conventions

| Type | Pattern | Example |
|------|---------|---------|
| Admin page | `{pluginId}--{routePath}` | `pro-workflows--workflows` |
| Editor panel | `{pluginId}--ext-{extensionId}` | `pro-workflows--ext-workflow-status` |

### Building Frontend

```bash
cd plugins/my-plugin/frontend
npm install
npm run build
# Output: ../dist/frontend/main.js
```

CE serves the bundle at `/api/v1/plugins/my-plugin/ui/main.js`.

### Menu Items

Menu items, menu groups and admin routes take a **label per locale** (`{ "en": "Workflows", "de": "Workflows", … }`). The sidebar, the dashboard cards and the breadcrumbs show the active interface language, then its base language, then English, then the first value you provided.

```typescript
getMenuItems(): PluginMenuItem[] {
  return [
    {
      section: 'content',
      group: 'editorial',            // optional: a PluginMenuGroup id
      label: { en: 'Workflows', de: 'Workflows', fr: 'Flux de travail' },
      icon: 'git-branch',            // Lucide icon name
      route: '/workflows',
      order: 10,                     // lower comes first; default 100
    },
  ];
}
```

An item without `group`, or whose group no active plugin defines, appears in the built-in **More** group, so it is always reachable.

### Styling with Tailwind

Plugin UIs ship **no stylesheet**: their custom elements render inside the host and use the host's Tailwind build. Tailwind only generates classes it finds in its content files, so the host scans `apps/web/plugin-classes.txt` — a committed list of every class token used in the plugin frontends. If your UI uses a class the host's own templates do not, regenerate the list:

```bash
# from the studio repository
pnpm --filter web plugin-classes                         # default: ../studio-pro/plugins
node apps/web/scripts/plugin-classes.mjs <pluginsDir> --check   # exit 1 when the list is outdated
```

<Callout kind="info">
  For the official Pro plugins this is automated: the `studio-pro` CI regenerates the list whenever a plugin UI changes and commits it to Studio, so the Docker image — built from Studio's sources only — contains the plugin classes.
</Callout>

<Callout kind="tip">
  Only use real Tailwind shades. A class such as `bg-gray-750` does not exist and silently renders nothing.
</Callout>

## Host Services

Besides the SDK, plugins can inject a few host services by injection token:

| Token | Purpose |
|-------|---------|
| `CONTENT_SERVICE` | Read and write content through CE (tenant-scoped, with events) |
| `CONTENT_SHAPE_SERVICE` | `migrateDataForType(orgId, contentTypeId, data)` moves data keyed by legacy form field ids to the type's storage paths. Use it for content data you store outside the content table (e.g. templates), so it matches the type after field storage moved to schema paths. Idempotent; unknown types are left alone |

## Best Practices

1. **Only import from `@roadbeat/plugin-sdk`** — never reference CE source
2. **Use event listeners** for extending behavior, not monkey-patching
3. **Handle errors gracefully** — a plugin crash should not break CE; throw coded HTTP exceptions, never a bare `Error`, for anything a client can cause
4. **Respect CE limits** — use `FeatureGateService.getLimit()`
5. **Version your plugin** with semver and declare minimum CE version in `requires`
6. **Use `pro_` prefix** for all database tables
7. **Test independently** with unit tests and mock factories
8. **Document your API** — use Swagger decorators on controllers
