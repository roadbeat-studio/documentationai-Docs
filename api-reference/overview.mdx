## Overview

roadbeat Studio exposes two distinct REST APIs:

1. **Management API** — full CRUD for content, assets, users, and settings (JWT auth)
2. **Delivery API** — read-only access to published content for frontends and apps (API key auth)

Both APIs are versioned under `/api/v1/` and return JSON responses.

<Callout kind="info">
  Interactive Swagger documentation is available at `http://localhost:3000/api/docs` when running the dev server.
</Callout>

## How this reference is organized

The endpoint pages in the sidebar are **generated from the API source code**: the Studio API emits its OpenAPI document straight from the controller metadata, which is split into one spec file per functional area (Authentication & Users, Content Management, Publishing & Distribution, … plus the Pro plugin areas). The reference therefore always matches the running API — including the `{ "data": ... }` response envelope and the standard error body documented below.

## Base URL

```
http://localhost:3000/api/v1/
```

In production, replace `localhost:3000` with your Studio domain.

## Response Format

All API responses follow a consistent envelope format:

```json
{
  "data": { ... },
  "meta": {
    "total": 42,
    "page": 1,
    "limit": 20,
    "totalPages": 3
  }
}
```

For list endpoints, the `meta` object includes pagination information. For single-item endpoints, only `data` is returned.

### Error Responses

Errors return an appropriate HTTP status code with a structured error body:

```json
{
  "statusCode": 409,
  "error": "Conflict",
  "code": "CONTENT_TYPE_IN_USE",
  "message": "Cannot delete content type \"event\": 12 content item(s) still reference it. Delete or reassign the content first.",
  "params": { "contentTypeId": "event", "count": 12 },
  "timestamp": "2026-11-08T12:34:56.789Z",
  "path": "/api/v1/manage/content-types/event",
  "requestId": "req_a1b2c3"
}
```

| Field | Description |
|-------|-------------|
| `statusCode` | The HTTP status, repeated in the body |
| `error` | The HTTP reason phrase (`Not Found`, `Conflict`, …) |
| `code` | **Stable, machine-readable error code.** Branch on this, never on `message` |
| `message` | English, human-readable description. A string for most errors; an array of strings (one per violation) for request-body validation errors |
| `params` | The values interpolated into `message`, e.g. `{ "count": 12 }` — present only when the error has any. Use them to build a translated message from `code` |
| `timestamp`, `path` | When and where the error happened |
| `requestId` | Echoes the `X-Request-Id` header for support and log correlation (`null` when none was sent) |
| `errors` | Per-field details — only on content validation errors, see below |

Every error thrown by Studio itself carries a **specific** code (`CONTENT_NOT_FOUND`, `USER_EMAIL_TAKEN`, `QUOTA_USER_LIMIT`, …). The few errors without one get a code derived from the status: a request-body validation failure becomes `VALIDATION_FAILED`, other errors `BAD_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `UNPROCESSABLE_ENTITY`, `TOO_MANY_REQUESTS`, `UPSTREAM_UNAVAILABLE` (`502`/`504`), `SERVICE_UNAVAILABLE` or `INTERNAL_ERROR`. Codes are stable across releases and are what the Studio UI translates into the interface language.

<Card title="Error Codes" icon="list" href="/api-reference/error-codes" horizontal={true} cta="Browse codes">
  Every error code with its HTTP status and meaning, grouped by area.
</Card>

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "code": "VALIDATION_FAILED",
  "message": ["email must be an email", "name should not be empty"],
  "timestamp": "2026-11-08T12:34:56.789Z",
  "path": "/api/v1/manage/users",
  "requestId": "req_a1b2c3"
}
```

| Status Code | Meaning |
|-------------|---------|
| `400` | Bad Request — validation errors, malformed input |
| `401` | Unauthorized — missing or invalid authentication |
| `403` | Forbidden — insufficient permissions for this action |
| `404` | Not Found — resource does not exist |
| `409` | Conflict — duplicate resource (e.g., email already taken) |
| `415` | Unsupported Media Type — upload type not allowed |
| `422` | Unprocessable Entity — content failed content-type validation |
| `429` | Too Many Requests — rate limit exceeded |
| `500` | Internal Server Error — unexpected server error |
| `502` | Bad Gateway — an upstream service failed (e.g. a Pro AI provider) |
| `503` | Service Unavailable — a required service is not configured or unreachable |

**Content validation errors** (creating, updating or publishing content) return `422` when the data does not satisfy its content type — including the cross-field rules (`after_field`, `before_field`), conditional requirements (`requiredIf`, `requiredUnless`) and referenced-item checks (`asset_exists`, `reference_exists`):

The body carries an additional `errors` array — one entry per rule that failed, each with a JSON-pointer `path`, a `message`, and the `keyword` that fired:

```json
{
  "statusCode": 422,
  "error": "Unprocessable Entity",
  "code": "CONTENT_SCHEMA_INVALID",
  "message": "Content does not match its content type schema",
  "timestamp": "2026-11-08T12:34:56.789Z",
  "path": "/api/v1/manage/content",
  "requestId": "req_a1b2c3",
  "errors": [
    { "path": "/end_date", "message": "must be on or after \"start_date\"", "keyword": "after_field" },
    { "path": "/cover_image", "message": "Referenced asset \"a1b2\" does not exist", "keyword": "asset_exists" }
  ]
}
```

`errors` appears only on validation failures that produce field-level detail; it is absent from other errors. The Studio content editor lists these entries against their field labels.

Plugin endpoints use the same body. Pro plugins build their exceptions against their own copy of NestJS; Studio recognizes them by shape, so a plugin's `404` or `409` keeps its status and code instead of turning into a `500`.

## Management API

The Management API requires **JWT authentication** and is used by the admin UI and internal tools.

### Endpoint areas

The sidebar groups every endpoint into one of these areas. Each is generated from the API, so the endpoint list under it is always current — browse there for exact paths rather than looking them up here.

| Area | Covers |
|------|--------|
| **Authentication, Users & Organizations** | Login and token flows, user accounts, organization settings, Delivery-API keys |
| **Content Management** | Content CRUD and versioning, content types, variants, relations and hierarchy, comments, layouts, Schema Registry import |
| **Localization & Reference Data** | Locales, translation tasks, machine translation, and the language / country / currency lists (the last three proxy the Context Directory) |
| **Assets & Media Delivery** | Upload, metadata, folders, tags, search, CDN integration |
| **Publishing & Distribution** | Discovery Node distribution, content pods, the Delivery API, exports and backups, outgoing webhooks |
| **Consumer Features** | Goals, follows, bookmarks, discovery, geo search, ActivityPub, Context Directory sync |
| **Platform, Administration & Operations** | Platform admin and onboarding, SSO exchange, federation, plugins, audit log, quotas, dashboard, search, health probes |

Licensed **Pro** plugins add seven further areas — editorial workflow, content operations, the AI assistant, the integration hub, governance and access, the GraphQL and realtime APIs, and media, layouts and notifications. Their endpoints only exist when the corresponding plugin is installed and licensed; see [CE vs Pro](/plugins/ce-vs-pro).

### Authentication

All Management API endpoints (except auth) require a JWT token:

```bash
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

See [Authentication](/api-reference/authentication) for details on obtaining tokens.

## Delivery API

The Delivery API requires **API key authentication** and provides read-only access to published content.

### Endpoint Categories

| Category | Base Path | Description |
|----------|-----------|-------------|
| **Content** | `/api/v1/delivery/content` | List and get published content |
| **Content Types** | `/api/v1/delivery/content-types` | Available content type schemas |
| **Assets** | `/api/v1/delivery/assets` | Asset metadata |
| **Layouts** | `/api/v1/delivery/layouts` | Content presentation layouts |

### Authentication

Pass your API key via header:

```bash
Authorization: Bearer rbk_your_api_key_here
# or
X-Api-Key: rbk_your_api_key_here
```

See [Delivery API](/api-reference/delivery-api) for details.

## Rate Limiting

All endpoints are rate-limited by default. Each request is counted in one bucket — per **user** for signed-in requests, per **API key** for Delivery API requests, per **IP** otherwise:

| Scope | Limit |
|-------|-------|
| **Global** | 100 requests per minute per user (JWT), per API key, or per IP (anonymous) |
| **Auth login** | 5 requests per minute per IP |
| **Password forgot** | 3 requests per minute per IP |
| **Password reset** | 5 requests per minute per IP |

Several editors behind the same office NAT each get their own budget. A forged, expired or malformed token counts as anonymous and falls into the IP bucket. The global limit is configurable — see [Configuration → Rate Limiting](/deployment/configuration#rate-limiting).

Rate limit headers are included in responses:

```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 95
X-RateLimit-Reset: 1706100000
```

When exceeded, the API returns `429 Too Many Requests`.

## Pagination

List endpoints support pagination via query parameters:

| Parameter | Default | Description |
|-----------|---------|-------------|
| `page` | `1` | Page number (1-indexed) |
| `limit` | `20` | Items per page (1–250) |

<Callout kind="alert">
  The parameter is `limit`, not `pageSize`. Unknown query parameters are rejected rather than ignored, so sending `pageSize` returns `400 Bad Request`.
</Callout>

Response includes pagination metadata:

```json
{
  "data": [...],
  "meta": {
    "total": 156,
    "page": 1,
    "limit": 20,
    "totalPages": 8
  }
}
```

A few high-volume endpoints use cursor pagination instead, replacing `meta` with `{ "limit", "hasMore", "nextCursor" }`. The endpoint's own page says which it uses.

## Filtering

List endpoints accept an allow-listed `filter[field]=value` convention. Each endpoint publishes the exact fields (and types) it will filter on. A field that isn't allow-listed is **rejected** with `400 QUERY_FILTER_UNKNOWN` (the message lists the allowed fields), never passed to the database, so filtering can never be used to probe unindexed or unintended columns. Likewise, a malformed value is rejected (`QUERY_FILTER_NOT_BOOLEAN`, `QUERY_FILTER_NOT_NUMBER`, `QUERY_FILTER_VALUE_INVALID`), as is a `sortBy` outside the endpoint's sortable columns (`QUERY_SORT_INVALID`).

```bash
# Only active API keys
GET /api/v1/manage/api-keys?filter[isActive]=true

# Discovery nodes in a given region
GET /api/v1/manage/discovery-nodes?filter[region]=eu-central
```

Multiple `filter[...]` parameters combine with AND. Filtering composes with `page`/`limit` and sorting.

## Versioning

The API uses URI versioning: `/api/v1/...`. Future breaking changes will be introduced under `/api/v2/...` while maintaining backward compatibility for v1.

## CORS

CORS is configured via the `CORS_ORIGIN` environment variable. In development, it defaults to `http://localhost:4200` (the Angular dev server).

## Compression

API responses are automatically compressed with gzip/deflate for responses larger than 1 KB.

## Health Checks

```bash
# Overall health, including dependency checks
GET /api/v1/health

# Kubernetes-style probes
GET /api/v1/health/live
GET /api/v1/health/ready

# Background job queues, and slow-query diagnostics
GET /api/v1/health/queues
GET /api/v1/health/slow-queries
```

See **Platform, Administration & Operations** in the sidebar for the response schemas.
